# Habits Tracker — Project Knowledge

## Application overview

A personal tracker for habits, expenses, chores, and a shopping list. It should run in a browser and on Android, with platform-specific presentation. The user has Android Studio installed.

The app uses Expo with React Native and React Native Web so it can target Android and the browser from one codebase. Platform-specific app shells provide different navigation layouts.

For local Android builds on this Windows machine, `android/gradle.properties` pins `android.cmakeVersion=4.1.2`, the installed SDK CMake package containing Ninja 1.12.1. Windows long-path support (`LongPathsEnabled=1`) is also required; restart Windows after enabling it so Android Studio and Gradle use the new setting. After changing toolchains, stop native builds and remove only the generated `android/app/.cxx` and `android/app/build` caches before rebuilding. These settings address the SVG codegen mkdir/path-length failure, not the harmless Java deprecation warnings. Expo prebuild regeneration can replace native configuration, so retain this CMake setting if regenerating the Android project.
The CMake pin was applied and both generated caches were cleared; Windows long-path support was subsequently verified enabled (`LongPathsEnabled=1`). A local `:app:assembleRelease` build completed successfully using JDK 21 and CMake 4.1.2. Its standalone APK is `android/app/build/outputs/apk/release/app-release.apk`; the JavaScript bundle, local fonts, and all four configured native ABIs were verified inside it. A debug APK expects a running Metro development server; the release APK packages the code and works independently of Metro. The generated release configuration currently uses the project's debug signing key for local testing. Physical-phone startup and functionality still need user testing.

## Main sections

- **Dashboard:** The front page, with statistics for the current month and calendar year.
- **Good Habits:** An independent tab for good habits. Users can add habit names.
- **Bad Habits:** An independent tab for bad habits. Users can add habit names.
- **Expenses:** Categories with custom colours, named expenses, dated payments in Romanian lei, income settings, monthly balances, a category pie chart, and a calendar.
- **Chores:** A separate tab with an active list, today's/overdue chores, and a planning calendar for one-off and recurring tasks.
- **Shopping List:** Saved products and supermarket prices, a separate bought checklist, and inventory quantities grouped by custom storage locations.

The dashboard summarizes the trackers for the month and year. Good Habits totals count completed habit-days, Bad Habits totals count recorded occurrence-days, Chores totals count actual completions, and Expenses sums recorded payments from Salary, Meal tickets, and Savings in the current local month and calendar year. Extra income, savings balance adjustments, loans, and loan repayments do not count as expenses. Expense values display Romanian lei. Numbers shown in design mockups are illustrative placeholders, not actual app data.

## Data and backup

- Save data locally on each device.
- Do not use cloud storage or automatic syncing.
- Provide manual JSON import and export for backups or moving data between devices.
- Backups contain entries, habit/chore tracking, an expenses ledger, and the shopping book. Exports use version 14; imports accept versions 1–14. Version 6 introduced monthly expense settings, version 7 added extra income/savings/loan history, version 8 added shopping and inventory, version 9 supports checklist products without supermarket offers, version 10 introduced optional amounts, version 11 places them on shopping-list entries, version 12 preserves bought history, version 13 adds optional inventory expiry dates, and version 14 preserves archived saved definitions. Device notification identifiers and browser delivery markers are not exported.
- Import validates the whole file before saving, then merges entries by ID. Imported names and types replace matching IDs while local-only entries remain. For matching habits or chores, supplied tracking replaces local tracking; older name-only entries preserve that category's local membership, plans, and history. Chore validation checks real dates, 24-hour times, repeat intervals/bases, unique plan/completion IDs, and completion links.
- Browser backups download as JSON and are selected through the browser file picker. Android Export JSON opens the system folder picker and writes a durable UTF-8 JSON backup directly to the chosen folder through Storage Access Framework; cancellation leaves data untouched. Import uses the system document picker. Exported files outside private app storage can be kept after uninstalling or clearing app data and manually copied to another device. Users should choose a local folder for local-only backups.
- Android uses the local `expo-sqlite` database `personal-tracker.db` in its private app directory. `snapshotStore.android.ts` commits changes in exclusive SQLite transactions, serializes reads/writes, enables WAL/full synchronous durability, and upserts only changed rows. `snapshotRows.ts` separates entries, habit dates, chore schedules/completions, each financial record, and each shopping/inventory entity into individually keyed rows; array order is retained. The app still derives its current screen state in memory from the complete validated snapshot.
- First Android loading validates and migrates the existing `habits-tracker:entries:v1` AsyncStorage value in one transaction, reads it back, and checks equality before committing the initialization marker. The original value is retained untouched as a recovery copy. Failed migration rolls back and blocks loading/writes; after initialization SQLite is authoritative and never falls back to outdated legacy data. Unknown schema versions and orphaned/invalid records are rejected. A fresh install without legacy data starts empty; preview/sample records are not seeded.
- Browser storage retains the same AsyncStorage key and whole-snapshot behavior through `snapshotStore.ts`; Metro selects SQLite only on Android. Shared validation, the App write guard, entry/financial/shopping preservation, and version 14 manual JSON import/export remain in place. Neither platform syncs automatically or uses a database server. Android `allowBackup: false` disables Google automatic app backup in new standalone builds; users keep backups through explicit JSON export and import. This build setting does not affect Expo Go and may not block manufacturer-specific device-to-device transfers. SQLite does not add application-level encryption or biometric locking.
- The Expo SDK-compatible `expo-sqlite` dependency is installed and locked. Existing standalone/development Android installations need a rebuilt binary to include the native dependency and backup setting. TypeScript checking passed for the storage migration and direct-folder export, and a subsequent standalone Android release APK build completed successfully. Native migration, folder export/import, and physical-phone functionality remain pending for user testing; no application test suite was run.
- Financial imports merge categories and payment records by ID and income settings by source/effective month. Incoming matching financial records replace local ones; local-only records remain. Older backups preserve the local ledger, expense assignments, monthly settings, and matching paid markers when those fields are absent; explicit null detaches an assignment. Importing an inactive category detaches its names and fixed settings, preserving payment history. Reference and one-monthly-payment-per-item/month validation runs before saving; equal expense names are allowed within and across categories.

Importing versions 1–12 preserves the local expiry for matching stock IDs; version 13 or 14 can replace or explicitly clear it. Android SQLite stores this metadata in the existing record payload, so no SQL schema change is required. Version 8 store-bound rows migrate by deriving productId from their offer, preserving IDs, bought states, paid prices, and inventory additions. Multiple legacy rows for one product are retained rather than discarding their stock undo links; new add actions block duplicate product membership. Validation checks identities, foreign keys, unit/count rules, sale bounds, optional purchase snapshots, and undo links. Older backups preserve local shopping. Stable-ID merges replace rather than sum stock; repeated imports are idempotent. Conflicting identities or broken references reject the entire import before saving.

## Expenses, incomes, and balances

- On web, ExpensesTab displays the selected month and five summary boxes ordered Salary, Meal tickets, Salary left, Meal tickets left, Total left. Income gear controls retain their existing behavior. A full-width rounded table shows category headers across the first row, each with its expenses stacked vertically underneath and an Add expense + in the header. Regular rows show paid record name, amount in lei, and Salary/Meal tickets source, with no checkbox or additional payment button. They are filtered to the selected month; a new month starts empty while categories remain. Navigating back restores saved rows, balances, chart, and calendar counts. Archived categories reappear without an Add button when they have records in the selected month. Payments appear below the category table; the category pie and calendar share a row below Payments on wide browsers. Narrow web browsers stack category columns and overview panels. The large Record a payment button and the entire selected-day card beneath the calendar remain omitted. A selected calendar day is the default date for new payment forms.
- Android Expenses uses the approved Category focus design: a teal Total left card, a collapsed Income & balances panel containing the two income controls and their remaining amounts, and Categories/Spending/Calendar section tabs. All categories are separate full-width rounded cards, including Monthly expenses, with independently toggled contents. Headers show the category colour/name, paid total for the selected month, a reserved chevron, and an independent + action. Long names wrap without covering either control. Monthly items retain their paid/undo checkboxes and settings; regular items retain name, amount, and funding source. The selected section precedes the compact payment summary. Switching sections keeps the selected financial month/date, so calendar navigation also updates category rows, chart, balances, and history. These presentation states are local to the screen; financial storage and web layout are unchanged. Shared Button provides accessible expanded disclosures and compact selected section buttons rather than separate Android controls.
- ExpenseBook in Resources/types.ts stores categories, records, income versions, extraIncomes, savingsAdjustments, loans, and loanRepayments separately from TrackerEntry names. Older local ledgers acquire empty arrays for the new history when parsed. A regular Add expense uses the createPayment action to atomically append a name and a dated payment, immediately deducting its chosen funding source. Names may repeat within or across categories; no name ownership/removal step is required. Legacy unpaid names remain stored without becoming payments or visible monthly rows. The Unassigned column and regular assignment workflow are no longer exposed. TrackerEntry.expenseCategoryId still links individual saved IDs for legacy data and recurring list membership; null detaches the ID without changing historical payments.
- A fixed Monthly expenses category is always available via expenseCategories. It adopts an existing active category of that name or displays a virtual default until its first item is saved. The category cannot be removed; individual items may be detached. Other categories and colours keep their existing behavior.
- Monthly items store an optional TrackerEntry.monthlyExpense amountBani/source setting, chosen in Add expense with Monthly expenses selected or the item's settings action. Rows show a checkbox, expense name, formatted monthly amount, and Salary, Meal tickets, or Savings source. Already paid rows show the original payment's amount/source; editing the fixed setting affects future checks without rewriting older payments.
- Checking a monthly item creates one payment tagged monthly for that item/month and deducts only its saved source. Unchecking removes that payment and restores its exact amount. A new month remains unchecked until explicitly paid; no income-period change or timer creates an automatic expense. Current-month checks use today's date; past-month checks use the selected calendar day. Future-month checks are disabled. Amounts and source stay visible while unchecked.
- Monthly payments feed the same balances, category pie, calendar counts, monthly/yearly Dashboard totals, and payment history as other records. Direct createPayment rejects the Monthly expenses category, preserving the fixed-amount checkbox flow. Removing a monthly payment from history also clears its checkbox. Detaching an item clears its fixed setting while preserving past payments; adding it back to Monthly expenses requires selecting a fixed amount/source again.
- Options creates categories with the shared ColorPalette (12 labelled swatches), adds expenses, removes monthly list items, and removes categories. ExpenseEditorModal reuses TrackerDialog, Button, Dropdown, DatePicker, and TextBox. Add expense fields are ordered Category, Expense name, Amount, Paid from, Payment date; a category header + preselects its category. Monthly expenses uses Monthly amount and Deduct from, omits the payment date, and creates no payment until checked. Successful regular saves retain category/source/date, clear name/amount, stay open, and confirm the amount deducted and source. Income saves also stay open; removal actions close after successful persistence. Saving disables financial text/select controls and rejects duplicate submissions and dismissal.
- Shared Dropdown shows a placeholder for values removed from its choices, disables empty lists, and closes empty popups, preventing internal IDs or blank option panels from appearing.
- Each payment stores date, amountBani, Salary, Meal tickets, or Savings source, optional note, stable IDs, and snapshots of its expense/category names and category colour. Payment dates must be today or earlier. Removing a category archives it and detaches its names; earlier payments, pie slices, and historical category totals are retained. Removing a payment requires a dedicated confirmation and restores its funding source's balance.
- Payments this month is a compact total/count summary with a View payments button. The button opens the shared TrackerDialog for the selected month, using its bounded ScrollArea, custom scrollbar, X, footer Close, outside dismissal, and Android Back. History rows show name/amount together, category/date/funding source beneath, and any saved note; the existing remove action opens confirmation and returns to the updated history after dismissal or successful removal. Empty months show an empty-state message. The full history is rendered only while its dialog is open, so it no longer increases the page height.
- Money uses integer bani with a 1,000,000,000,000-bani per-amount bound and safe-integer aggregate validation. parseLei accepts comma or dot decimals (up to two places) and rejects ambiguous separators, negatives, extra decimals, and unsafe values. formatLei uses Romanian decimal/group formatting followed by lei. Payments must be positive; incomes may be zero. Overspending is shown as a negative remaining balance rather than blocking factual payment entry.
- Initial Salary and Meal tickets amounts apply to the current local month. All later amount/receipt-day changes become effective on the first day of next month and propagate forward; repeated edits replace only that pending month/source version. Historical and current-month income amounts remain unchanged. Each source has a monthly receipt day (1–31), clamped to the last day of shorter months. Receipt dates are displayed, while boxes represent the whole monthly budget rather than a bank account ledger.
- Salary left = applicable monthly salary minus salary-funded payments for that month. Meal tickets left uses the corresponding meal-ticket income and payments. Total left is Salary left + Meal tickets left + that month's Extra income; Savings is excluded. Each month starts with its applicable amounts; the previous month's unused budget is not counted as new income. Future-dated imported records are excluded until their date arrives.
- Extra income is a dated positive amount, added using its card's + action through ExpenseEditorModal. It affects only the chosen month's Extra income and Total left, does not repeat, is not a spending source, and never changes Salary, Meal tickets, the expense chart, or dashboard spending.
- The Extra income and Savings cards use neutral product copy on both platforms: "Other income received this month." and "Funds reserved for future expenses."
- Savings has its own card beside Extra income on web and Android. Its gear opens the live current balance for editing, independently of the displayed month. Setting it stores a dated signed adjustment equal to the target minus the current balance; past months are not rewritten. The running balance is all adjustments minus Savings-funded expense payments through the selected month's end (capped at today). It carries across months. Both ordinary and fixed monthly expenses offer Savings alongside Salary and Meal tickets. Paying reduces Savings and counts in spending/history/charts; removing a payment or undoing a monthly checkbox restores its exact amount. It never changes Total left.
- Loans is a dedicated category panel with an Add loan action and rows showing only each loan's name and remaining amount. Android expands it independently. Add loan saves a name, original positive amount, and date; its row action opens a repayment amount/date form. Repayments reduce only the debt, with no funding selector, expense record, account deduction, pie slice, or dashboard spending. Overpayments, nonpositive amounts, future dates, and repayments dated before the loan are rejected. Loans and repayments carry across months, with remaining amounts calculated at the selected month's end (capped at today); fully repaid rows remain visible with zero and a disabled repayment action.
- All new forms reuse TrackerDialog, TextBox, DatePicker, and Button, remain open with success messages after saves, and use the existing duplicate-write/dismissal guards. Version 7 exports include all four new history arrays; validation checks dates, safe integer bani, unique IDs, loan references, and cumulative repayments before a storage write or import. Snapshot merges combine each history by stable ID, are idempotent, and preserve the local new history when importing older formats. Current-format backups missing those arrays are rejected.
- ExpensePieChart uses the existing react-native-svg dependency, category colours, an accessible chart summary, and a legend with category amounts/percentages. A React Native View around the SVG owns accessibility props, avoiding invalid boolean SVG attributes on web. Empty and single-category months have explicit render paths. No external chart library, currency service, account, backend, or paid service is used.
- Dashboard Expenses tiles show current-month/current-year recorded spending in lei. Each opens the selected period's category pie and payment breakdown. Creating names/categories or changing income amounts does not count as spending. Shared StatCard allows currency values to shrink within compact metric tiles.
- Dashboard also shows the shared ExpensePieChart for actual current-month payments and the shared Chores Calendar. Web at 1000 px and above has aligned rows: Month/Year summary cards, then pie/chores calendar beneath their respective cards. Android and narrower web stack Month, Year, pie, then chores calendar. Calendar counts and selected-day details reuse listChoreOccurrences with the same 42-day grid, archived completions, and completion-based repeat estimates as ChoresTab. Selecting a day shows names and Done/Due/Overdue/Estimated status, local reminder times when present, and European dates. This is an overview with no planning or completion writes; the existing metric breakdown dialogs remain available. Saved changes in other tabs and midnight/app-resume refreshes update the overview from the existing entries/ledger, without new storage fields.

## Visual direction

The approved direction is a calm, cartoon-inspired interface with restrained soft-clay 3D depth across components.

- Android keeps the browser's loaded Nunito 400/600/700/800 faces.
